# 项目线

学生做课设、毕设、竞赛之前，先查这件事有没有人做过、做到什么程度、哪部分能直接用。

## 先判断值不值得查

**两问判入**（都过才往下走）：

1. **这个题目有技术实现的部分吗？** 纯文献综述、纯社会调查、纯问卷分析没有，“做一个 XX 系统 / 工具 / 算法”有。
2. **用户是不是要真做出来？** 交个报告就完事的不值，要跑起来、要演示、要答辩的值。

两问都不过，说明这是选题咨询不是技术落地，直接答，别硬套流程。

**确认技术栈约束**：进入后先看用户是否把语言或框架定死（例如限定 Java/Spring Boot 或 Python/Vue）。定死了就只查该技术栈下有没有现成实现；没定死则按常见课设栈放开检索。

## 检索

按 `references/repos.md` 的方法查。若用户直接给出某个候选 GitHub 仓库链接询问“能不能用/怎么改”或需核验真伪，直接运行 `python <skill_dir>/scripts/github_lookup.py --repo "<URL或owner/repo>"` 一次拿齐体积、许可证风险、归档状态、`src/` 结构与 README 中间件线索。做选题检索与查重时，最少覆盖两个来源（有浏览器能力时补足第三个）：

1. **GitHub** — 有接口，中文关键词也能搜
2. **通用搜索** — 用「题目 + 毕业设计 + 源码」这类组合，或 `site:gitee.com <题目> 毕业设计`
3. **Gitee（可选）** — 国内课设项目多，但无可用公开接口，仅在有浏览器能力时作为补充源

关键词怎么组：

- 题目核心名词 + 技术栈：`图书管理 springboot`
- 中文搜一次，英文再搜一次：`library management system`
- 加限定词找学生项目：`毕业设计`、`课程设计`、`大作业`

## 排序：把“能不能跑”放第一位

这一节是整个项目线的核心。普通搜索按星数排，那是给工程师看的。学生要的是能跑、能读、能量身改。

| 优先级 | 看什么 | 怎么判断 |
|---|---|---|
| 1 | 能不能跑起来 | 有没有安装步骤、有没有依赖清单（`pom.xml` / `package.json` / `requirements.txt`）、有没有建库脚本 |
| 2 | 代码量读不读得完 | 仓库体积。超过 50MB 基本是工程项目；**低于 100KB 的先看有没有 `src/` 目录，可能只是刚建仓或纯文档**；几千行以内的才好改 |
| 3 | 依赖复不复杂 | 要不要装 Redis、消息队列、搜索引擎。学生机器跑不动三个中间件 |
| 4 | 技术栈匹配 | 用户说 Java 就别推 Python |
| 5 | 许可证与维护状态 | 有无协议、是否强传染、最近一次代码提交（`pushed_at`） |
| 6 | 最后才看星数 | 星高的是框架不是课设。星数只说明“有人用”，不说明“适合你改” |

### 许可证风险分类（必须明确标注）

- **宽松协议（MIT / Apache-2.0 / BSD）**：可作为学习骨架或合规复用，按协议保留声明。
- **强传染协议（GPL / AGPL / LGPL）**：**衍生代码通常必须以同协议开源**；商业竞赛、闭源项目或学校禁止强传染开源的场景须提前预警。
- **自定义协议（GitHub 返回 `NOASSERTION`）**：代表非标准协议、双协议或特殊限制，**必须点开仓库 `LICENSE` 文件人工核对**后再决定能否复用。
- **无许可证（`license: null`）**：默认保留所有权利，**不能拿代码**，只能放进“仅参考思路”。

## 输出三块（紧凑直给原则）

为避免信息重复、减轻阅读负担：**总览表控制在 3~5 行以内**；下方“逐项判断”**只详细展开真正推荐复用的 1~2 个首选骨架**。用户点名询问但不合格的仓库用 2~3 句简明交代原因即可；无许可证（`license: null`）的参考仓只在总表和查重表标注“无许可证-仅参考思路”，不单独展开长段模块拆解。

### 一、能直接用的

项目名、地址、语言、规模、最后更新时间、许可证类型、它完整实现了什么功能。地址必须贴出来，不能只给名字。

### 二、要改的部分

逐项说：这个项目的哪些模块能留、哪些必须换成你的、为什么换。

分三类讲清楚：

- **通用能力**：登录注册、权限、分页、文件上传、图表。这些每个课设都写一遍，直接用现成的，不要自己造。
- **要改的**：业务逻辑、数据模型、界面。这部分是你的工作量。
- **不能用的**：它特有的、跟你的题目无关的模块。直接删。

### 三、坑

这个方向学生最常踩的重复劳动、已经有成熟方案的地方。

写的时候具体，不要写“注意性能”这种空话。要写“这个项目用了 Redis 做缓存，你没装 Redis 就跑不起来，先在配置里关掉”。

## 创意查重

用户担心选题烂大街时做这一步。

做法：把题目拆成 2-3 个功能关键词，各搜一次，取最接近的 5 个项目。

输出三样：

1. 每个项目覆盖了什么功能
2. 它没做什么（这是你能下手的地方）
3. 你的题目跟它重叠在哪

**不给相似度百分比。** GitHub 搜索是关键词匹配，算不出语义相似度。写一个“相似度 73%”就是编的，比不给更糟。

结论只写一句：这个方向已经做到哪一步，你的差异点只能放在哪。

## 项目线硬规则

除 `SKILL.md` 共用的四条外，补充项目线专属规则：

1. **不能跑的不算推荐。** 没有说明、没有依赖清单、只丢一个压缩包的，标成“仅参考思路”，放在最后。
2. **不替你写代码。** 给路线、给模块划分、给要改的地方。代码让 AI 写完，答辩你讲不出来。
3. **不推荐整包照抄。** 说清哪些是通用能力（用现成的），哪些是你的工作量（自己写）。
4. **维护状态要说。** 半年没提交的项目照样能推，但要写清“这个项目 2024 年之后没更新”。

## 需要打断的两种情况

- 题目太宽（“做一个管理系统”），先问清管理什么、给谁用
- 用户想要“能直接交的完整代码”，先说明这条线只给路线，不给成品

## 工作量估计

给粗估，不要精确到天：

- 骨架能不能用：能直接用 / 要改一半 / 只能参考思路
- 主要工作量在哪：前端 / 后端 / 数据库 / 算法 / 部署
- 最容易超期的是哪一步

学生最不会估时间。给他一句“这块大概两周，最容易卡在环境配置上”，比给他一个路线图有用。
